# 项目评测

这组 M6 评测回答两个问题：在同一项目起点和验收条件下，Terse 能否指出复制实现，并让复用或清理后的版本通过；对合理新增、独立职责和不确定引用，能否保留正确的处置边界。

评测使用仓库自带的多文件订单项目，是可复现的受控工程案例。它实际创建 Git 工作区、运行 `begin → context → check` 和 Node 验收测试，不调用模型。它不代表已在外部生产仓库完成评测，也不测量 agent 是否因此主动改变编码选择。

## 运行与产物

需要 Node.js 24+ 和 Git，在 Terse 仓库中运行：

```sh
npm ci
npm run evaluate
```

`npm run evaluate` 构建后执行 [评测脚本](../scripts/evaluate.mjs)，成功时退出 0 并输出一个 JSON 报告；任何行为或检查结果偏离预期，脚本会失败退出。要单独测试评测入口：

```sh
npm run build
node --test test/evaluation.test.mjs
```

常规 `npm test` 已包含评测和旧示例，CI 不再额外运行评测命令。测试诊断日志提供每个变体的行为结果、状态、重复组数、规则与耗时。运行数据保留在 `.terse/evaluation-<随机后缀>/`：

- 每个 `<场景>-<变体>/` 是独立 Git 项目，保留变更后的源码和相同验收测试。
- `.terse/runs/<run>/` 包含基线、检索记录、决策和完整检查报告。
- 根目录 `evaluation.json` 汇总基线与验收哈希、候选、出现次数证据、源文件/行数、各阶段耗时及报告绝对路径。

产物只保存在本地，不提交、不自动上传；CI 中的摘要可从日志查看，完整工作区不会跨 CI 运行持久保存。重新运行会生成新目录；这些目录包含源码，按项目缓存规则管理。

## 项目与实验约束

[原订单模板](../examples/orders) 提供权限隔离、金额校验和 CSV 编码；[评测补充文件](../examples/evaluation) 增加应用入口、按任务组织的验收测试。任务包含调用迁移、公开 facade、旧实现淘汰和新领域功能，而非只在一个函数内比较行数。任务与人工编写的预期处置集中在 [evaluation-cases.mjs](../scripts/evaluation-cases.mjs)。

每个变体独立执行以下流程：

1. 从同一模板建立源码与策略，采集基线。成对变体的初始源码和基线快照哈希必须相同。
2. 用真实 `context` 检索预期候选；通知任务必须没有匹配候选。候选命中不表示语义理解或检索质量已全面达标。
3. 保存决策，安装同一份任务验收；实现编辑器只接收 `src` 的读写接口。实现修改后核对测试哈希及配置未变化。
4. `check` 运行原订单测试、调用入口测试和任务验收三个文件。成功变体必须确认三项测试均执行；悬空引用变体必须真实验收失败。
5. 按任务预期检查状态、行为结果、重复是否出现、必要的清理规则和报告持久化。同一场景的测试哈希必须相同。

扫描策略统一为 `minTokens: 50`、`minLines: 5`、`duplicatePolicy: review`；排除 `test` 的重复扫描，但验证命令始终执行这些测试。实现正确性和检测规则分别记账。示例与评测共用 Git/CLI 辅助函数；从 Node 测试启动 CLI 时清理 `NODE_TEST_CONTEXT`，避免嵌套测试运行器只执行首个验收文件。

## 当前结果

首轮本地 Node 24 / Windows 观察如下；每次运行都会重新断言这些预期。组数是 `newDuplications`，不是完整仓库的重复率；行数包括入口和类型定义，只作变化信号。

| 任务 | 变体 | 行为验收 | Terse 状态 | 新增重复组 | 业务源码行数（前→后） |
| --- | --- | --- | --- | --- | --- |
| 修改：增加付款状态筛选 | 新增复制的导出模块 | 通过 | needs-review | 1 | 27→49 |
| 修改 | 在原流程增加可选筛选 | 通过 | pass | 0 | 27→27 |
| 删除：淘汰 legacy 实现 | 调用迁移，旧实现保留 | 通过 | fail | 0 | 48→48 |
| 删除 | 删除文件，调用未迁移 | 失败 | fail | 0 | 48→27 |
| 删除 | 删除文件且迁移调用 | 通过 | pass | 0 | 48→27 |
| 重构：提取 reporting 模块 | 复制实现并保留旧函数体 | 通过 | needs-review | 1 | 27→48 |
| 重构 | 移动实现并保留薄导出 facade | 通过 | pass | 0 | 27→36 |
| 合理新增：幂等通知队列 | 新增独立职责 | 通过 | pass | 0 | 27→33 |
| 独立职责反例：审计导出 | 不同权限与跨 owner 可见性 | 通过 | needs-review | 1 | 27→48 |
| 不确定性反例：插件动态加载 | 删除旧文件，运行时选择新实现 | 通过 | needs-review | 0 | 50→28 |

修改和重构两组配对中，复制与复用版本通过相同验收，新增重复由 1 组变为 0 组。这证明这两个案例存在可检出的重复和满足验收的复用途径。重构后行数仍增加，因此不以减少行数作为通过条件。

删除场景验证了重复计数不能替代清理：历史副本未删时新增重复仍为零，但 `REMOVAL_REMAINS` 阻止通过；悬空调用产生 `REMOVAL_REFERENCE_REMAINS` 和真实验证失败；完成迁移后通过。

审计导出与客户导出共享一段格式化 token，但权限与可见性不同，预期保持待评估。该发现是正确的 token 相似证据；若将它自动解释为“必须合并”，则会误用结果。动态加载的验收通过，也不能证明所有动态消费者已迁移，`REMOVAL_REFERENCE_UNRESOLVED` 保留 review。正常的新通知职责没有可复用候选并可通过，不因新增文件而失败。

## 报告含义与限制

报告 `schemaVersion: 1` 描述此评测汇总格式，与 CLI 的同名版本分别使用；`kind` 为 `controlled-project-evaluation`。记录工具版本、运行时平台、仓库 HEAD、每个变体的预期和实际结果。HEAD 标识代码起点，未提交的工作区修改不由该字段证明；正式复现应使用干净的指定提交。

`timingsMs` 记录包含进程启动的 begin/context/check 墙钟时间和整个变体耗时，用于本机成本观察，不保证跨硬件可比。`model` 和 `tokenUsage` 为 `null`，原因明确记录为未调用模型，不能将空值解释为节省了全部 token。

这 10 个手工变体不是随机样本。它们能回归已知成功、失败和 review 边界，不能估计一般误报率、漏报率、业务职责等价性或大仓库性能。尚未进行外部项目授权采样、多模型多次运行、盲评、实际修复轮次和 token 对照；这些是下一轮评测范围。核心分析器、阈值和 CLI 契约均复用现有实现。
